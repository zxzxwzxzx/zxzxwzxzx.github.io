UniWM / 项目摘要

研究问题

视觉导航需要把对环境的理解转化为行动。将世界建模与导航规划分开处理，可能使模型预测的未来状态与实际选取的动作不一致。UniWM 将视觉预测和动作规划放入同一个多模态自回归框架，并通过分层记忆结合近期观察与较长的轨迹上下文，使规划能够参考预测的视觉结果。

我的工作

我参与这一方向的研究，重点负责在 1X Humanoid 数据上搭建完整实验代码与训练评测流程，把传统机器人导航方法迁移到 25-DoF 人形机器人设置。工作目标是验证方法能否跨越不同自由度的机器人形态，并通过与 NWM 的对照实验分析导航成功率和轨迹误差。

实验结果

在论文报告的 1X Humanoid 数据集实验中，完整模型导航成功率为 81%，NWM 基线为 51%；ATE 从 0.57 降至 0.28，RPE 从 0.24 降至 0.14，相对降低 50.9% 和 41.7%。这些结果支持了方法向高自由度人形机器人导航迁移的有效性。

LANGUAGE-CONDITIONED WORLD MODELING

LCVN 语言条件视觉导航

背景与任务

LCVN 研究仅给定初始第一视角观察与自然语言指令时，智能体如何完成导航。任务不依赖目标图像，因此需要将语言意图与视觉预测、连续动作联系起来。论文探索了在想象的隐空间中学习策略，以及统一自回归预测动作和观察两种路径。

我的工作

我参与项目的代码实现，负责整体实现与模型训练、测试流程，把模型运行、基线对照和评测连起来。在项目中，我的贡献集中于算法实现与实验执行，使语言条件导航方法能够在相应任务和数据设置下得到验证。

实验结果

在论文 v1 的测试集对比中，LCVN-Uni（k=2）成功率为 36%，NWM(lang) + LCVN-AC（k=4）为 22%；ATE / RPE 分别从 1.31 / 0.44 降至 0.65 / 0.22。对应相对降幅为 50.4% / 50.0%，指标为完整模型结果。

02

自动化竞品评测

AGENT / EVALUATION

把语音采集、批量测试与异常接管串成持续运行的评测流程。

我的职责 · 自动化评测链路开发

背景与目标

语音竞品评测需要持续采集多个模型的交互结果。随着模型数量和测试量增长，人工逐项灌测、检查脚本运行并处理采集异常，会占用大量时间。项目的目标是形成可批量运行的采集测试链路，并减少异常情况下对人工值守的依赖。

技术方案与个人工作

我搭建了覆盖 GPT、Gemini 等 10+ 模型的评测链路，将回环采集与批量测试结合起来。采集脚本负责常规任务，Agent 负责监控运行状态与异常接管。问题定位围绕硬件、浏览器、模型应用三个维度展开，分别排查设备与采集链路、页面与自动化运行状态、应用响应与交互问题。

现有链路结果

链路每日产出 10,000+ 条评测数据，灌测人力投入减少 76%。异常自愈率达到 90%，多数异常无需人工介入，使人工精力能够更多地用于结果分析与需要进一步排查的问题。

Agent 职责与交接

检查项与修复链路：扩展设计

三个定位维度为硬件、浏览器和模型应用。以下检查项、交付格式及修复—测试—恢复验收流程是围绕现有采集守护补充的设计方案。

01 / 硬件定位 Agent
检查音频输入输出设备、采集链路和录音信号，区分设备不可用与无有效音频。
交付：设备状态、录音样本、异常环节及判断依据。
02 / 浏览器定位 Agent
检查麦克风权限、会话状态、页面变化及自动化操作是否到达预期页面状态。
交付：页面状态、操作记录、复现步骤及异常位置。
03 / 模型应用定位 Agent
检查请求与响应、错误提示、响应超时和对话轮次，区分应用侧异常与采集侧故障。
交付：响应证据、受影响模型、失败轮次及归因结论。
04 / 修复 Agent
根据定位证据选择受限修复：设备重连、页面或会话恢复、操作适配、可重试请求重试；保留回退方式。
交付：修复动作、变更范围、执行结果与待验证用例。
05 / 测试 Agent
复现原始失败用例，再检查相邻用例；同时验证音频有效性、对话轮次与结果完整性。
交付：通过 / 失败结论及证据；失败时返回修复环节。
06 / 恢复验收 Agent
测试通过后先恢复小批量采集，观察任务状态和数据产出；确认稳定后再恢复正常任务。
交付：恢复结论、观察记录；仍有异常时转人工处理。

协调与退出：由协调层汇总异常证据、归因结论和已执行动作，派发给对应 Agent。跨维度结论冲突时先补充证据；修复有范围和次数限制。证据不足、超出修复范围、重试用尽或验收失败时，保留现场并交由人工处理。

AI 面试平台

REALTIME / FULL STACK

面向外包人员与多语种发音人面试，连接内部配置、公网语音交互和结果复核。

我的职责 · 管理端、面试端与后端全栈开发

背景与约束

业务需要让外部人员通过邀请链接完成语音面试，同时由内部人员维护面试配置、查看录音与转写、完成复核。公网不能直连内部数据库，面试过程还需要处理授权、设备检查、重复开始、断线和提交重试等情况。我的工作是完成管理端、面试端与后端开发，将配置发布、语音交互和证据回收连成可交付的流程。

架构决策与实现

平台拆分为内网管理面与公网运行面：内部 RDS 保存面试定义、邀请与复核数据，公网只维护执行当前面试所需的运行状态。配置发布由 Snapshot Publisher 从发布队列领取任务，校验快照标识与内容哈希后下发；结果回收由内网的 Result Collector 主动拉取事件和提交清单，通过游标、租约和幂等处理支持重复执行。两条同步链路均由内网发起，公网不持有内部数据库访问能力。

语音交互与过程留存

平台接入 Seed Realtime 及组合式语音能力。受限 Voice Gateway 按面试会话校验语音通道权限与服务端截止时间，适配 ASR、Seed 2.0 和语音输出，并同步当前话题、候选人与面试官的转写。录音按双方音轨分别登记，提交时将回答、音频引用、转写和快照关联到同一份清单，供内部回放和人工复核。

结果与应用

平台已上线用于外包人员交付，支持从邀请、授权、语音面试到结果回收与人工复核的完整业务流程。版本化快照使每次面试对应明确的配置，原始录音与转写为后续检查保留依据；重复请求和同步重试通过运行态与提交契约进行约束。

关键模块与工程细节

依据功能验收记录与仓库实现
01 / 管理与配置发布
内部 SSO 与角色权限控制管理入口，支持候选人、面试、题目和邀请管理。语言、题目、最大尝试次数及时间限制固化为不可变快照；重复发布同一内容可幂等处理，同一标识内容冲突时拒绝覆盖。
02 / 面试运行状态
邀请兑换短期浏览器会话，完成登记、授权与开始前检查后进入面试。同浏览器重复开始复用当前尝试，不同浏览器不能并行占用同一邀请；服务端控制次数和硬截止，重连不延长截止时间。

按会话授权接入语音能力，保存带角色与话题信息的转写。候选人与面试官音轨分别编号，已登记片段禁止被不同内容覆盖；提交前检查必答题及语音证据是否齐全。

从新增查重、存量清理到发布检查，减少 Skill 重复与选取冲突。

Kaboo

CONTRIBUTOR / RELIABILITY

优化客户端菜单栏快照更新：先展示可用数据，再以受控工作量推进后台刷新。

我的职责 · 项目贡献者 · 客户端菜单栏快照稳定性优化

背景与问题

Kaboo 客户端菜单栏通过本机服务获取一份展示快照，汇总 Token、统计图表、额度与运行状态。我的优化针对这一快照的更新过程：当单轮承担过多处理工作时，刷新容易超时，影响面板更新的稳定性。因此需要限制一次更新的工作量，同时让未完成部分能够继续推进。

技术决策：为每轮更新设置边界

将更新改为分批限量处理与断点续跑。每轮从此前保留的进度继续，处理本轮允许范围内的数据；达到单轮上限后停止继续处理，保留本轮结果和续跑进度，剩余内容留到后续更新。这样将完整更新拆成多轮推进，单轮可以及时结束，尚未处理的数据也有明确的后续处理路径。

结果与作用

优化后，客户端菜单栏单次快照更新平均耗时为 1.5 秒。限量处理控制了单次更新的规模，续跑机制使未完成部分能够逐轮补齐。这项贡献聚焦快照更新的稳定性；Kaboo 平台整体覆盖 1 万+ 内部用户，为优化提供了实际使用场景。

系统已有机制与个人优化
01 / 先展示缓存，再异步刷新
普通快照读取请求优先返回当前可用缓存；需要更新时再触发后台构建。没有缓存时先返回占位快照。日志扫描与用量上报是独立流程，打开菜单栏不等于重新扫描全部日志。
02 / 个人优化：单轮限量与续跑
为一次更新设置处理上限，达到上限即停止本轮继续处理，保留结果和进度，未完成内容留给后续更新。把可能过重的一次工作拆成多轮，控制单轮响应时间。
03 / 避免重复刷新与过期结果写回
已有刷新任务运行时，客户端不会再启动同一轮后台刷新；构建器通过锁协调更新。发布时校验设置版本与账号认证版本，避免异步任务在切换设置或账号后写回过期结果。
04 / 按字段保留可用数据
构建器合并统计、热力图与额度等分区。请求失败且字段缺失时，在缓存身份、时效和设置允许的范围内复用旧值；成功返回的空结果仍然有效，不能用旧数据覆盖真实的零值或空值。

两类缓存各司其职：本地用量缓存保存按时间桶聚合的使用数据；最近可用快照保存面板需要的汇总 JSON。上报完成与快照刷新分别进行，因此刷新状态和各数据分区的时效需要分别判断。

指标口径：1.5 秒为本人提供的客户端菜单栏单轮快照更新平均耗时；1 万+ 为平台整体用户规模。
